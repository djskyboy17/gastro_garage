# Staff access, v5

One shared kitchen workspace, public sign-in shell, explicit membership. Site authentication remains unchanged. Trust only Sites-injected identity; no passwords or client-selected identities. A public Site is not automatic workspace access.

Owner bootstrap: deploy the confirmed owner's email as runtime secret KITCHEN_OWNER_EMAIL, never source or migration. Only an identity with that platform-supplied email may claim the single owner binding. Registration atomically inserts the singleton owner and membership; no first-visitor administration. After binding, ownership uses stable Site user ID and cannot be changed through the application. Missing setup configuration fails closed. No production local-auth bypass.

Every signed-in account can request access for itself; repeat requests preserve roles including disabled. Admins see requests and may grant admin/dispatcher/kitchen/warehouse/courier, leave pending, or disable. Owner is immutable; an administrator cannot change its own role. Revisions and atomic audit guard competing changes. Revocation applies on the next server request; previously viewed data cannot be withdrawn from a browser.

Permission policy is an allowlist in domain.ts. Unknown write paths deny by default. Owner/admin have all declared operations; dispatcher manages catalog/customers/orders/delivery/payment; kitchen changes only production state; warehouse manages recipes, stock and procurement. Demo seeding and access administration require admin. Courier master records may be connected explicitly by an admin to an approved courier-role member. Courier role has no generic staff/data access and uses the dedicated /courier surface; see ../courier/SPEC.md. Revocation automatically unlinks the account.

Read projections: dispatcher sees sales/delivery but no stock, purchasing or global audit. Kitchen sees anonymized order labels, operational order notes, item quantities/allergens and production, with customer contacts, prices, payment, couriers, procurement, inventory and audit removed. Warehouse gets recipes/stock/procurement and anonymized order demand, without sales prices, customer/contact details, delivery records or global audit. Blank/redacted fields render as unavailable rather than zero financial values. Role-specific navigation and actions mirror server enforcement. Admin members list is separately protected. Pending/disabled accounts cannot read workspace data or write business records.

API: GET /api/session; POST /api/access/request; GET /api/access/members; POST /api/access/role. Every API response is no-store. POST requires same-origin JSON and platform identity. Caller role is loaded from DB on each request; no client/session role caching as authority.

Acceptance: no anonymous access or forged role/header escalation; unapproved user cannot read data; registration never resets a blocked user; kitchen can start cooking but cannot edit payment; warehouse can receive goods but cannot modify customers; dispatcher cannot modify recipe or roles; owner/self demotion rejected; stale updates do not create extra audit; HU/RO UI and reload preserve effective role. Local integration tests seed temporary role fixtures in the local-only D1 database and restore the owner afterward; no production test endpoint exists.
