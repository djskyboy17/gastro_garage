# Recurring weekly order templates, v7

Manual generation only. Owner/admin/dispatcher manage templates and generate orders. No scheduler, messages, subscriptions, payments, tax documents or automatic supplier orders. Kitchen/warehouse cannot read template/customer configuration or operate generation; generated ordinary orders follow their existing projections and workflows.

Templates reference one customer, 1–10 unique products and integer portion quantities. Weekly days use ISO 1=Monday through 7=Sunday, with an inclusive start/end window, local delivery time and optional excluded dates within the window. An active flag pauses generation; edits use revisions. No automatic holiday calendar. Dates are kitchen-local calendar days, not UTC recurrence timestamps; enumeration uses UTC noon only for date arithmetic to avoid DST shifts.

Preview accepts an inclusive range of at most 31 days, starting today or later. It intersects the template window, selected weekdays and explicit exceptions. Current active products, gross integer-bani prices, allergens, names, latest recipe IDs and customer delivery details are resolved server-side. No negotiated template-specific price yet. Preview shows existing occurrences separately. Its SHA-256 content fingerprint must match at generation; a changed template/catalog/customer/recipe requires a new preview. Existing-occurrence flags are deliberately outside the fingerprint so concurrent overlapping generation remains idempotent.

Generation is an atomic D1 batch: guard template revision/activity with a non-null run reference, insert missing orders, insert unique template/day occurrence mappings, insert only the new run's item snapshots, audit newly created orders and run. JSON rowsets keep statement count bounded even for 31 days. Nothing consumes stock or marks payment/production/delivery complete. Records start confirmed/queued/pending/unpaid with no courier. Each generated order captures independent snapshots as ordinary order creation does.

One template/day creates at most one order, enforced by a unique DB index and deterministic order ID. Repeating a range or overlapping concurrent runs skips existing occurrences. Cancelled occurrences are still existing and are not silently recreated. Later template changes, pauses, exclusions or generation never overwrite, add items to, or cancel existing orders. Handle existing orders in Orders. A generation UUID retry returns its original created/skipped IDs even after a template changes; a changed request with the same UUID conflicts.

API: POST /api/recurring/templates, /preview, /generate; read templates/occurrences via role-projected GET /api/data. All APIs use existing authenticated membership, same-origin JSON, validation and no-store responses. No schema writes at request time. Source reference for bounded JSON rowset SQL: https://developers.cloudflare.com/d1/sql-api/query-json/.

Acceptance: weekday/date/window/exclusion/DST boundaries; invalid ranges and past generation denied; recipe and price snapshots; stale preview/config denied; sequential retry and concurrent overlapping generation create one occurrence/item set/audit per day; edits and cancellations do not alter or recreate existing orders; paused templates deny new runs; role enforcement; HU/RO UI preview then explicit generation, reload persistence and ordinary kitchen/delivery visibility.
